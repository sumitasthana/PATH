# Notebook guide

Start here when sharing the repository or opening it in Colab. Notebook numbers show when a notebook was added, not a sequence to run from 01 to 20. Choose the notebook for the job. Historical notebooks stay at their original paths because experiment records and earlier links cite them.

Open the main workflows directly in Colab: [04: gradient diagnostic](https://colab.research.google.com/github/sumitasthana/CARK/blob/main/notebooks/04_gradient_diagnostics.ipynb), [07: paired L9 probe](https://colab.research.google.com/github/sumitasthana/CARK/blob/main/notebooks/07_paired_L9_probe.ipynb), [08: paired report](https://colab.research.google.com/github/sumitasthana/CARK/blob/main/notebooks/08_paired_L9_reporting.ipynb), [09: experiment overview](https://colab.research.google.com/github/sumitasthana/CARK/blob/main/notebooks/09_experiment_overview.ipynb), or [10: evidence export](https://colab.research.google.com/github/sumitasthana/CARK/blob/main/notebooks/10_export_experiment_evidence.ipynb).

## Use and share results

Notebooks 15 through 20 use R2. Earlier GPU experiment notebooks save to Drive before releasing the runtime. CPU notebooks read saved files in a fresh session; do not expect Python variables to survive a Colab disconnect. Record experiment results in the [Experiment trajectory](https://github.com/sumitasthana/PATH/wiki/Experiment-trajectory). Original experiment files are preferable when available.

For experiment-06 generalization, open [18 in Colab](https://colab.research.google.com/github/sumitasthana/CARK/blob/main/notebooks/18_paired_study_prepare.ipynb), then [19](https://colab.research.google.com/github/sumitasthana/CARK/blob/main/notebooks/19_paired_study_run.ipynb) for bounded GPU sessions, and [20](https://colab.research.google.com/github/sumitasthana/CARK/blob/main/notebooks/20_paired_study_review.ipynb) for CPU review. Keep the same study ID and fixed settings to resume. Each notebook pins a committed implementation revision; use Colab or a clean checkout when the local repository has unrelated training edits. This all-images diagnostic matrix is separate from the reserved-image recovery study in 16 and 17.

Notebook 19 now uses the selected-seed queue for existing study `paired_generalization_v2`: order 01, the chosen seed, its source and L15 control, then U3/L15 and U14/L15. Change only `SEED` to 0, 1, or 2 and run all cells on A100. Training is enabled by default. Completed jobs are reused. The remaining study jobs are deferred, and the saved plan is unchanged. Do not rerun PREPARE for this continuation. The session attempts at most four unfinished jobs within its 120-minute soft budget and 15-minute save reserve. A new seed needs a fresh eight-lesson source and may require several sessions. Keep the same seed until its selected queue finishes. Use the same study ID in notebook 20; its full-study summary remains partial until the other jobs are completed. One completed seed is a pilot, and additional completed seeds allow variation across seeds to be measured.

Notebook [21](https://colab.research.google.com/github/sumitasthana/CARK/blob/main/notebooks/21_forgetting_collapse_check.ipynb) checks what a forgotten model actually predicts. The paired study records exactly 10.0% for every forgotten task, and accuracy alone cannot separate a model that guesses from one that answers the same class for every image, because 500 validation images split evenly over 10 classes give exactly 10.0% for one fixed answer. The notebook loads a finished source model from R2, applies one forgetting request with the study's settings, and records the per-class prediction counts and the size of the generated weights every 20 steps. It measures the protected tasks at the same points, so their normal variation acts as a control on the measurement. It is read-only: it trains no source model, writes nothing into the study, and cannot disturb a resume. Its optional upload goes to a separate diagnostics folder. A few minutes on A100; CPU works but is slow. It does not test whether forgotten information can be recovered, which is the separate study in 16 and 17.

Notebook [22](https://colab.research.google.com/github/sumitasthana/CARK/blob/main/notebooks/22_fixed_noise_forgetting.ipynb) tests the suspected cause of that collapse. The paper's Algorithm 2 draws a new random target at every unlearning step, and averaging over many fresh zero-centred targets pulls the generated weights toward zero rather than toward noise, which is why the model stops responding to its input. The notebook runs four variants on one saved source model: a never-trained network as the reference the paper describes, the study code, the same loop copied into the notebook with fresh targets, and that loop with a single fixed target drawn once and reused. The third exists to prove the copied loop reproduces the study code, so any difference in the fourth comes from the noise target and not from the rewriting. The changed loop lives in the notebook, so the repository stays at its pinned revision and existing study results stay valid. One seed, A100, a few minutes. It does not reproduce the paper's configuration and says nothing about the authors' reported numbers.

Notebook [23](https://colab.research.google.com/github/sumitasthana/CARK/blob/main/notebooks/23_learn_after_unlearn.ipynb) asks whether learning task 15 repairs the damage that unlearning does. Notebook 22 measured the model at the moment unlearning stops, where every protected task sits near chance, but the paired study only ever reported accuracy after task 15 had been learned, and by then those tasks had largely recovered. This notebook measures all three moments: before unlearning, straight after it, and after task 15. It runs a control that only learns task 15, the published method at 100 steps, and the fixed noise target at 100, 300 and 800 steps, all from one saved source model, then reports whether the other tasks recover to the control, whether the forgotten task relapses above the study's 12 percent limit, and whether task 15 still learns. Learning is the slow part, so allow around an hour on A100. One seed, beta 0.1 against the paper's 0.01 for Tiny ImageNet.

Notebook [24](https://colab.research.google.com/github/sumitasthana/CARK/blob/main/notebooks/24_recovery_probe.ipynb) asks whether a forgotten task can be brought back cheaply. It unlearns task 3 once at the study's own setting, then runs three arms from that same model with the same images and the same number of steps: an attacker keeping the task's original code and BatchNorm statistics, a fresh start with a brand new code and reset statistics, and the code alone with statistics reset. Recovering faster than the fresh start is what would show information survived; the third arm separates out the BatchNorm statistics, which unlearning never touches even though they derive from the forgotten task's images. Budgets of 1, 5 and 20 images per class, taken from task 3's own training set. About fifteen minutes on A100. A failure to recover is reported as ambiguous rather than as evidence of removal.

Notebook [25](https://colab.research.google.com/github/sumitasthana/CARK/blob/main/notebooks/25_figures_for_talk.ipynb) draws the five figures that summarise the unlearning result, for a talk or a write-up. It needs nothing: no GPU, no R2 credentials, no checkpoints and no dataset, because the measurements are copied in as plain numbers and it runs on matplotlib and numpy alone. The figures are what a chance-level score should look like against what was observed, where the model sends the 500 test images as unlearning proceeds, generated weight size against input sensitivity on a log scale, three states that all score near ten percent, and recovery under the authors' frozen procedure. A final optional cell re-downloads the saved runs and checks the copied numbers against them; without credentials it reports that it was skipped and the figures are unaffected. A last cell writes every figure to PNG. Run all takes a few seconds.

Notebook [26](https://colab.research.google.com/github/sumitasthana/CARK/blob/main/notebooks/26_plasticity_baseline.ipynb) measures plasticity, meaning the ability to learn a new task, which is a separate question from forgetting. The study already ran the two later arms under other names: its control jobs learn task 15 after the eight tasks of order 01, and its branch jobs learn it after an unlearning request. What never existed is the baseline those scores should be compared against, a generator that has learned nothing taught task 15 alone, so the notebook reads the finished arms from R2 and trains only that. It runs the baseline twice, because a first task is allowed to train the chunk embeddings and a ninth task is not, and the frozen version is the fair comparison. Input sensitivity sits beside every accuracy, since a model that has stopped reading its input scores ten percent and so does a model that guesses. Two task-15 learning runs per seed on A100; sections 1 to 5 read the existing arms and need no GPU. Needs the three R2 secrets. One probe task and one order, so a positive result is not a general claim about this generator.

Notebook [27](https://colab.research.google.com/github/sumitasthana/PATH/blob/main/notebooks/27_weight_change_and_sensitivity.ipynb) puts the two model measurements side by side on one unlearning request, and is the first notebook to take them from the shared module `uncle/measure.py` rather than from a copy. Input sensitivity had been pasted into notebooks 21, 22, 23, 24 and 26 as five versions that had drifted apart; the module holds one, including the switch to evaluation mode that the collapse measurement depends on. The module also adds `relative_change`, which is the quantity the adapter plasticity study in `reference/adapter-plasticity-study` calls `rel_dW`: the size of the weight change divided by the size of the weights it started from. Reading the two together is the point. Over 100 unlearning steps the weights move an ordinary amount while input sensitivity falls by a factor of several million, so a weight measurement on its own would not have found the problem. The notebook runs from `main` rather than the study's pinned revision, because the module was written after the pin, and it checks the unlearning code against the pin before using it. A few minutes on A100, slower on CPU. Needs the three R2 secrets. It trains no source model and writes nothing into the study.

Notebook 20 now defaults to `paired_generalization_v2` and saves its summary JSON, study configuration, CSV tables, and any generated PNG/SVG figures to R2 automatically in its final cell. Uploads have progress bars and content verification. The cell prints the timestamped R2 export location only after every artifact has been verified. Run all cells on CPU to regenerate exports from saved reports; no training is required.

Notebook 19 displays one compact panel beside the running cell. It shows the narrowed study's 12 jobs, six comparisons, and 39 requests across seeds 0, 1, and 2, plus the selected seed's four jobs and 13 requests. These are counts of saved completed work, not estimates of GPU time. The current request shows learning steps and epoch/loss, unlearning steps, validation, or dataset/R2 transfer progress. Transfers update the same panel instead of appending a line for every chunk. A verified-save timestamp distinguishes saved progress from the current live steps. The deferred jobs in the original matrix are excluded from these totals. Display changes preserve the saved training revision and resume state.

The default permanent model storage is approximately 4.84 GB for nine sources, plus small reports. Two large active resume slots can add roughly 4.3 GB temporarily. Completed branch models are uploaded and verified before a durable completion receipt is saved and the model is removed. Report review checks that receipt instead of requiring a deleted model. Keeping branch finals or post-unlearning models is an explicit configuration option, set before study preparation.

Share the ZIP from notebook 10 when another person needs the evidence. It includes the tracked code version and file hashes, but it cannot recreate unsaved Colab output. Start with notebook 09 when the person only needs an explained visual overview. Every chart should be read with its source and limits, especially when comparing one seed or one paired run.
